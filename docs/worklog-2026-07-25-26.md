## Part I — Token-2022 unblock (commit `2ec0c9a`)

### The bug

A wallet-funded raw cycle builds `[CU ixs, setup(create ATAs), swap1, swap2, teardown]` in
one transaction. For `USDC→ANSEM→USDC`, `setup` creates the intermediate ANSEM ATA. It used
`create_associated_token_account_idempotent(&user, &user, &ANSEM, &spl_token::id())` — the
**classic** SPL program. ANSEM's mint is owned by **Token-2022** (`spl_token_2022::id()`),
so the CreateIdempotent failed `IncorrectProgramId`, reverting the whole tx (and, because
it's a raw tx that *did* include on-chain, burning base + priority fees — a Jito bundle
failure is free; a reverted raw tx is not).

Two things were wrong, not one: an ATA's address embeds the token program in its PDA seeds,
so a classic-derived ATA address is **also wrong** for a Token-2022 mint. Both the *create*
instruction **and** the swap's user source/destination accounts had to switch programs.

### The fix

Thread the correct program per mint via `Pool::token_program_for(a_side) -> extra.token_program_a/b`
(defaulting to `spl_token::id()`), through every place an ATA is derived or created on the
wallet-funded path:

- **`src/arbitrage/evaluator.rs`** — while building swaps, gather `mint → token_program` into
  a map; derive `user_src`/`user_dst` with `get_associated_token_address_with_program_id`;
  pass the map to `build_setup_instructions`, which now creates each ATA under its own program.
- **`src/dex/dlmm.rs`** — `token_x_program`/`token_y_program` from `token_program_for()`
  instead of hardcoded classic (Orca + Raydium CLMM already threaded it; DLMM was the gap).
- **`src/arbitrage/pool_check.rs`** — same per-mint program for the sim/probe ATAs.

### Safety property

Classic mints resolve to `spl_token::id()`, so every derived address and instruction is
**byte-identical** to before — only Token-2022 mints change. New test
`setup_creates_token2022_intermediate_ata_under_t22_program` asserts a Token-2022
intermediate's ATA is created under the T22 program (and the classic ATA is *not*). Build
clean; `dlmm` 7/7, `setup` 3/3 green.

### Not fixed (deliberate)

The **flash-loan** setup path (`flash_loan.rs`, SOL base) still hardcodes classic — a
separate follow-up. It is off the wallet-funded raw path (USDC base force-disables flash),
so it does not block anything here.

### The other half: the pool DATA (commits `1fb6e5a`, `75b992e`)

The code fix was only half. Once the focused book went **live**, the raw tx
`USDC→ANSEM→USDC` fired for real (`route: raw-rpc`, +25820 USDC-units, no tip, 62 ms) and
**still reverted `IncorrectProgramId` at instruction 2** — the intermediate ATA create. The
binary was confirmed to *have* the code fix (built 10:11 UTC, after the 09:29 commit; failed
at 10:57). The gap: `token_program_for()` reads `extra.token_program_a/b`, but the
**DLMM/Orca/Raydium fetchers never emit that field** (only `fetch_pumpswap_pools.js` does), so
ANSEM's + PUMP's pools shipped with it unset → the code correctly read the data, and the data
said "classic." The code asked the right question; the data gave the wrong answer.

Fix: `scripts/backfill_token_programs.js` queries each mint's on-chain owner
(`getMultipleAccounts`) and stamps `extra.token_program_a/b` for Token-2022 sides (classic
left unset → Rust default). Pure `applyTokenPrograms` is unit-tested + idempotent. Applied to
`pools.json`: **6 sides** (ANSEM×2, PUMP×4 — the arb targets; momentum pump pools already
carried it from the pumpswap fetcher). Because a re-scan rewrites `pools.json` without the
field, `arb_refresh_loop.sh` now runs the backfill between `scan --apply` and the SIGHUP, and
blocks the reload if it fails. **Durable follow-up:** teach the DLMM/Orca/Raydium fetchers (or
the scanner's decode step) to emit `token_program_a/b` directly, so the backfill becomes a
belt-and-suspenders pass rather than load-bearing. **Lesson:** a Rust-side "Token-2022 fix"
that reads a pool-config field is only as good as the fetcher that populates it — verify the
data, not just the code, before calling it done.

## Part II — Raw-RPC FOCUS mode (commit `44bed9a`)

### Why

General 3-hop-via-SOL arb has never landed profitably: every cycle went through Jito, and
the tip auction ate thin edges (the 07-05 investigation). The one thing that lands is the
**raw-RPC carve-out**: a wallet-funded 2-hop `USDC→X→USDC` cycle small enough for one
≤1232-byte tx with zero ALTs, sent via plain `sendTransaction` — no tip, no auction, valid
on every leader slot. So the book should stop carrying general arb and focus entirely on
tokens that form that shape.

The targets are **graduated pump.fun tokens with ≥2 USDC venues** (ANSEM, PUMP). Fresh
cross-quote memecoins (e.g. Jotchua) have a *single* USDC pool — a round-trip through one
pool is a guaranteed loss, not an arb — and are correctly excluded.

### The scanner rewrite (`scripts/scan_arb_pools.js`, `scripts/lib/book_budget.js`)

Gated by `ARB_RAW_RPC_FOCUS` (default **on**). The book becomes:

| Bucket | Rule |
|---|---|
| **Keep (core)** | momentum-watcher pools **+ SOL/USDC/USDT hub↔hub pricing pools** |
| **Admit** | fresh movers with **≥2 USDC venues each ≥ `ARB_RAW_MIN_USDC_LIQ`** ($50k), USDC legs boosted ×`ARB_RAW_RPC_BOOST` (3.0) |
| **Drop** | majors, general memecoins, broad fetcher pins; general incumbents **not** carried forward |

- **Why hubs stay:** `pools.json` is shared with the momentum watcher, which prices SOL/USDC
  off it for portfolio valuation and the SOL-price poller the tip-sizer depends on. Dropping
  the hubs would break EUR/USD reporting. This was the one dependency that made "remove *all*
  except momentum" wrong.
- **Why the majors fall away without a name-list:** RAY/mSOL/ETH also have ≥2 USDC venues,
  but they're stable *incumbents*, not fresh movers — and the arb scanner inherits
  `MOMENTUM_SCAN_RANK=change`, so `scan_tokens` only surfaces movers. Low-volatility majors
  never appear in discovery, so dropping them is automatic once incumbents aren't carried.
- **`rawRpcEligible` gained a per-leg `minUsdcLiq` floor** so a thin USDC pool (whose
  DexScreener spread is a stale-price artifact, not a real edge) can't qualify a token.
  `book_budget.isProtected` gained an `ctx.rawFocus` branch; flag-off = byte-identical legacy
  behaviour.

### Safety guard: never collapse to core-only

Birdeye discovery is **rate-limited and flaky** — the first report run returned
`0 discovered`, seconds later a direct run returned 2 tokens. If focus mode wrote a book on
a `0 discovered` scan, it would strip every arb target *and* the working pins, idling the
bot. The scanner now **refuses to write a book with zero raw targets** (a "raw target" is any
pool that's neither momentum nor hub↔hub — a floor leg or a fresh admission), exiting `10`
(unchanged) so the working book persists until discovery recovers.

### Verified (report mode, nothing written)

raw-RPC eligible: PUMP (4 USDC venues) — 2-hop, boosting USDC venues ×3

Plus a `0 discovered` run that correctly refused to collapse.

## Part IV — the raw path needed a simulation gate (commit `03ffe83`)

Live again, the Token-2022 cycles stopped reverting — but a **different** failure appeared: a
thin `USDC→SOL→USDC` **hub** cycle (1.25 bps) reverted at the Meteora DLMM leg,
`ExceededAmountSlippageTolerance` (6003). `getTransaction` on the failed sig confirmed the ATA
CreateIdempotents succeeded under the classic Token program (Part I holds) — only the swap
slippage-reverted.

Root cause: the raw path sent with `skip_preflight: true` (a deliberate latency choice), so
unlike the Jito path — which calls `simulate_opportunity` and silently drops a divergent cycle
— it fired blind. Every hop's `min_out` is `quote × (1 − SLIPPAGE_BPS)`; with the operator's
`SLIPPAGE_BPS=10` and a 659 USDC input, the DLMM impact-model divergence exceeded the 10 bps
buffer and the on-chain swap fell short → revert → **base + priority fee burned** (a failed
Jito bundle is free). Efficient hub pairs (SOL/USDC) do this constantly; the real targets are
the volatile pump tokens.

Fix: `skip_preflight: false`. The RPC now simulates before forwarding — a divergent/thin cycle
is rejected **pre-send** (no fee, no propagation) while a genuinely profitable cycle passes and
lands. The no-auction raw path absorbs the sim RTT and still lands on the next leader slot. A
preflight reject is the same unprofitable cycle the Jito path would sim-reject, so the arm keeps
its conservative no-Jito-fallback.

**Operator note:** with preflight on, `SLIPPAGE_BPS` now also governs how many cycles get
*rejected* (a reject ⇔ on-chain divergence > `SLIPPAGE_BPS`). At `SLIPPAGE_BPS=10` +
`INPUT_BASE_UNITS=800 USDC`, expect many free rejects — the safe failure mode. To land more,
lower the input (less impact divergence) or loosen slippage (worse fills). **Deeper root cause**
(not fixed): the DLMM/CLMM `get_quote` impact model is optimistic at size — preflight is the
safety net, not a cure. Accurate quotes are a separate, contested-code follow-up.

## Part V — the DLMM quote + a structural no-loss guard (commits `ecb1125`, `e3a86c2`)

Two follow-ups to Part IV's preflight net, to stop *generating* the divergent cycles rather than
just rejecting them, and to make slippage tuning safe.

**DLMM quote was zero-impact (`ecb1125`).** `dlmm::get_quote` multiplied by the raw active-bin
price with `price_impact: 0.0` — infinite-depth assumption, so it overestimated the fill for any
input that crosses bins (the direct cause of the `ExceededAmountSlippageTolerance` reverts). It
was the *only* CL venue missing an impact term. Gave it the **same conservative CP-marginal
haircut Raydium CLMM already uses** (`impact = in/(reserve_in+in)`, output × (1−impact), off the
vault reserve DLMM already tracks). Under-fills rather than over-fills, so the evaluator stops
sizing into reverts. Not exact DLMM bin math (uses total vault liquidity, not active-bin depth) —
preflight stays the correctness net; this just cuts the volume of doomed submissions.

**No-loss floor on the final hop (`e3a86c2`).** Every hop's `min_out` was `quote × (1−SLIPPAGE_BPS)`,
including the closing hop — so a cycle whose quoted margin was below the slippage buffer could
*land* below break-even (a real loss), because the profit gate only checks the *quoted* margin and
preflight only checks that `min_out` is met, not that `min_out` clears cost. That made
`SLIPPAGE_BPS` a choice between reverts (tight) and losses (loose) — and answered the operator's
"is 50 reasonable?" with **no**: at 50, any cycle with margin < 50 bps could land ~0.5% under water.

Fix: floor the final hop at `max(quote × (1−slippage), gross_out − (net_profit − min_profit))` —
i.e. principal + all costs + min_profit, provably ≤ `gross_out` once the profit gate passed. Now
**slippage governs only the reject threshold; profitability is structural** — a divergent closing
fill reverts / preflight-rejects (free) instead of landing at a loss. Intermediate hops keep their
slippage target; `net_profit` (the ternary objective) is computed before the floor, so sizing is
unchanged. `breakeven_min_out` is a pure, unit-tested helper.

**Operator guidance settled:** keep `SLIPPAGE_BPS` tight (~10); it now only trades land-rate for
free rejects, never for losses. The remaining knob is quote accuracy — the DLMM haircut helps but
a true bin-aware model is the deeper, still-open follow-up.
